## 调度层（替代 LiteOS-M）

`app/los_compat.c` 提供与原 LiteOS 同名接口，应用层代码不用改 `#include`：

- **任务**：`los_sched_add(名字, 步进函数, 周期ms, 优先级)`。调度器按
  “上一拍起始 + 周期” 排下一拍，步进函数自己花的时间会自动从等待里扣掉，
  所以采集是真实 250ms 节拍。
- **队列**：`LOS_QueueCreate/WriteCopy/ReadCopy`，环形缓冲，读写都不阻塞
  （应用层原本就全部用 `LOS_NO_WAIT`）。
- **互斥**：单线程顺序执行，加锁退化为关中断。
- **时基**：SysTick 1ms，`board_millis()` / `LOS_TickCountGet()` 都读它。
- **节拍兜底**：仿真器里若 SysTick 中断没打通（`s_tick` 一直不动），调度器会先重新使能
  SysTick，连续多轮仍不动就软件补一拍，保证“退化运行”而不是静默卡死。
- **栈**：所有任务共用主栈（链接脚本 `_estack` 起向下生长），bss 约 22KB，RAM 128KB，余量充足。

任务表：

| 步进函数 | 周期 | 作用 |
|---|---|---|
| `ProcessControl` | 50ms | 工序状态机 + 执行器输出 |
| `Control` | 50ms | 环境控制、事件上报、快照 |
| `CaneSensors` | 350ms | HX711 / 超声 / 红外 / MQ2 采集 |
| `Display` | 20ms | 按键、语音轮询、2.8 寸屏刷新 |
| `Sensors` | 250ms | 安全量采样（烟感走 250ms 是为了报警快） |

> 原来的 `Valve`（18ms）任务已删除：舵机改用 TIM4 硬件 PWM 输出，写一次 CCR 就能一直保持角度，不需要再按拍打脉冲。

## 2026-10-30 傍晚：舵机改到 PD14 + 煮糖页语音

**舵机不转的真正原因**：电路里三只舵机的 PWM 通过端子接到 MCU（端子靠 `PinId` 同名自动同网）：

| 舵机 | 端子 | PinId | MCU 引脚 | TIM4 通道 | 代码字段 |
|---|---|---|---|---|---|
| 分装阀门 servo_1 | `Tunnel_67` | PD13 | PD13 | CH2（CCR2） | `servo[0]` |
| 入料闸门 servo_2 | `Tunnel_73` | PD12 | PD12 | CH1（CCR1） | `servo[1]` |
| 液体出料闸门 servo_3 | `Tunnel_74` | **PD14** | PD14 | CH3（CCR3） | `servo[2]` |

而过滤阀的动作原先写在 **PD4**（`Tunnel_F407_228`），这条端子在电路上没有任何对端，等于往空脚发脉冲——所以舵机一直不动。

改动：

1. `cane_hal.c` 的 `cane_servo_frame()` 不再手工拉高/拉低 PD4，直接写 `TIM4->CCR3`。
   TIM4 已配成 1MHz 计数 + ARR=19999（20ms，50Hz），CCR 500/1500/2500 对应 0/90/180 度，硬件持续保持角度。
2. `app_runtime.c` 删除 `Valve` 任务（不再需要反复打脉冲）。
3. `cane_runtime.c` `cane_apply()` 里 PD14 舵机的三档角度：

| 工序 | 条件 | 角度 |
|---|---|---|
| 提纯 | 按 PC13 开过滤阀（`filter_open`） | **90 度** |
| 榨汁 | 液位到 180cm 排液 | 180 度 |
| 其他 | — | 0 度（关） |

## 2026-10-30 夜（二）：Makefile 按文件名搜源文件的坑

**报错**：`USER/main.c:11:10: fatal error: sys.h: No such file or directory`

**原因**：平台的 `USER/` 里残留着基础模板自带的 `main.c`、`syscalls.c`、`sysmem.c`。
旧 Makefile 是 `$(notdir)` + `vpath %.c $(sort $(dir $(C_SOURCES)))` —— 按**文件名**在目录列表里顺序搜。
`$(sort)` 把目录排成 `STM32F4xx_FWLib/src/` → `USER/` → `app/`（ASCII 升序），`USER/` 排在 `app/` 前面，
于是 `build/main.o` 被模板的 `USER/main.c` 抢走。那份文件 `#include "sys.h"`（正点原子风格），
而 `sys.h` 不在工程里，直接编译失败。

**为什么本地一直没发现**：`_localbuild.py` 是按绝对路径列表直接调 gcc，根本不走 make，所以这个坑只在平台上炸。

**改法**：

| 位置 | 改动 |
|---|---|
| `Makefile` | 目标文件改名为「路径下划线化」：`app/main.c` → `build/app_main.o`，`USER/system_stm32f4xx.c` → `build/USER_system_stm32f4xx.o` |
| `Makefile` | 删掉 `vpath` 和两条 `%.o: %.c` 模式规则，改用 `$(foreach)+$(eval)` 为每个源文件生成一条绑死路径的规则 |
| `Makefile` | `-MMD -MP -MF` 从 `CFLAGS` 挪进规则体（`eval` 会把规则文本二次展开，`$@` 那时是空的，会变成 `-MF""`，gcc 就把源文件当成 `-MF` 的参数吃掉） |
| `_rebuild/USER/` | 删掉模板残留的 `main.c`、`syscalls.c`、`sysmem.c`，只留 6 个真正参与编译的文件 |
| `_mkzip.py` / `_push2.py` | `USER/` 改成 6 个文件的白名单，不再整目录打包 |
| `_localbuild.py` | 目标文件名也带路径前缀；新增「同名残留」检查，提前报出 `USER/main.c` 这类冲突 |

**验证**：本机用 mingw32-make 真跑了一遍 Makefile（不是绕开 make），`exit=0`、text 86944、产出 elf/hex/bin；
平台 `build_status=1`、`error:` 0 条、text 86988。

> 教训：Makefile 里**永远不要**用 `$(notdir)` + `vpath` 去凑 object 名。
> 只要有第二个同名源文件（尤其是模板残留的 `main.c`），vpath 的顺序就会决定成败，而且不报"找到了两个"，只会给你一份错的。

## 2026-10-30 夜（三）：储存仓湿度过高报警（上限 70%）

**需求**：储存仓湿度超过 70% 要报警。

**实现**（`DHT11_1` 走 PA0，采集任务 2s 一次，值有效窗 5s）：

| 项 | 值 / 做法 |
|---|---|
| 报警阈值 | `AG_HUMI_ALARM = 700`（内部单位 ×10，即 70.0%） |
| 解除阈值 | `AG_HUMI_CLEAR = 680`（68.0%），2 点滞回，免得贴线抖动 |
| 故障位 | `AG_FAULT_HUMI_HIGH = 512`（独占一位，与其他 9 个故障位不重叠） |

顶栏状态点照样报警，但执行器继续按工序走。

**播报话术**：固定一句「当前环境湿度过高，请注意防潮」（宏 `HUMI_ALARM_TEXT`，定义在 `cane_runtime.c`）。

## 2026-10-31（第 2 轮）：PA7 电机不转 / 储存仓超温话术 / 提纯过滤流程

### 1. 榨汁、提纯、煮糖三个工序的 PA7 电机不转

| 项 | 内容 |
|---|---|
| 引脚 | **PA7 = TIM3_CH2**，由 `cane_hal.c` 的 `TIM3->CCR2` 输出（代码本来就在驱动） |
| 根因 | `board_port.c` 里 TIM3 时基是 **1MHz 计数 + ARR=999 = 1kHz PWM**。直流电机经驱动管做占空比调速，1kHz 太低：扭矩明显变小、电机一顿一顿，肉眼看就是"转一下停一下"甚至不动 |
| 修复 | TIM3 的 `ARR` 改成 **49** → **20kHz**；`cane_hal.c` 里风扇 `CCR1`、电机 `CCR2` 的换算系数同步从 `*10u`（满量程 1000）改成 `*50u/100u`（满量程 50） |
| 共用说明 | TIM3 的 CH1(PA6 风扇) 与 CH2(PA7 电机) 共用一个时基，频率只能取折中值。20kHz 对风扇调速无影响，且超出人耳敏感段，不会有异响 |

三个工序的期望占空比：榨汁 `stir=70`、提纯 `stir=60`、煮糖（到 102℃）`stir=50`。

### 2. 入仓工序温度过高话术

| 场景 | 话术 |
|---|---|
| 糖块入库工序（PA0 / DHT11_1 储存仓探头） | **「储存仓环境温度过高，请立即采取对应措施」** |
| 其余工序（车间环境） | 「蔗糖厂温度过高，请检查车间通风」 |

改动落在 `cane_runtime.c`：

* 新增宏 `STORE_HOT_TEXT`；
* `alarm_reason()` 里按 `proc.stage==PSTAGE_STORE` 分流；
* 报警播报处对这句话**豁免「安全报警，」前缀**，否则会念成"安全报警，储存仓环境温度过高…"；
* `PAGE_STORE` 的整页播报也接了这条：超温时直接念整句，不再只念"温度多少度"（原来现场从页面播报里听不出已经超限）。

判定阈值本身没变：`AG_FAULT_AIR_HOT`，≥40℃。

### 3. 提纯环节完整流程

```
进入提纯 → UI 固定显示浑浊度 45%
         → 播报「杂质过多，请手动开启提纯过滤」
         → 按 PC13（第 4 个键）
         → PD13 舵机转 90 度开过滤阀
         → 播报「打开过滤阀门」
         → PA7 直流电机带过滤网运行，浑浊度 45% → 10%
         → 到 10% 停电机，播报「浑浊度下降到10%，过滤完成」
```

**舵机分工重排**（网表 `Tunnel` 的 `PinId` 已逐条核对）：

| 舵机 | 引脚 / 通道 | 职责 |
|---|---|---|
| `servo[0]` | **PD13** / TIM4_CH2 | 称重加料阀（分装 180°）+ **提纯过滤阀（90°）** |
| `servo[1]` | PD12 / TIM4_CH1 | 入料闸门（进料 180°） |
| `servo[2]` | **PD14** / TIM4_CH3 | 液体出料闸门，**只在榨汁液位满时排液 180°**，不再兼任过滤阀 |

> 用户原话是"驱动 PD14 的步进电机转 90°"，同时又要求"把 PD14 的液体出料闸门改到 PD13 的称重加料阀位"。
> 实现上按**动作发生在新位置 PD13** 处理 90°，PD14 只保留榨汁排液，两个动作互不干扰。

其它细节：

* 进提纯时先复位 `filter_req / filter_open / filter_done`，否则第二批进提纯会直接跳过按键；
* `CANE_VALVE_OPEN_DEG = 90`，`CCR = 500 + 90*2000/180 = 1500us`（TIM4 时基仍是 ARR=19999 = 50Hz，未动）；
* 阀没开时电机不转、浑浊度锁在 45%；
* 过滤没走完（`filter_done=0`）按「下一步」会被拦下，提示"浑浊度还没降到10%，请先按PC13开启过滤阀门"；
* `cane_process_next()` 用 `say_seq` 快照保护，进工序的专属播报不会被"下一步，已手动进入…"导航句冲掉。

自检脚本 `output/cane_final3_test.py`：**42/42 PASS**（含 90° 脉宽反算、三条话术文本、PD13/PD14 通道映射）。

## 2026-10-31（第 3 轮）：PA7 榨汁 / 搅拌电机三个工序都不转

**现象**：榨汁、提纯、煮糖三个工序里，PA7 上的 `dcmotor_1` 完全没有动画。

**排查结论**：软件链路和 GPIO 配置都是通的，问题在**驱动方式选错了**。

| 检查项 | 结果 |
|---|---|
| `p->stir` 在三个工序是否赋值 | ✅ 榨汁 70 / 提纯 60 / 煮糖 50 |
| `c->motor=p->stir` | ✅ `cane_apply()` 里正常传递 |
| `cane_outputs()` 是否写输出 | ✅ 每拍都写 |
| PA7 最终是否 AF 模式 | ✅ `board_af(GPIOA,7,GPIO_AF_TIM3)` |
| **`dcmotor_1` 元件属性 `hz`** | ❌ **2000** —— 模型按 2kHz 采样引脚电平 |

**根因**：上一轮为了修「电机抖动」把 TIM3 从 1kHz 提到 **20kHz PWM**。但平台
`dcmotor` 元件是 `lPin->PA7 / rPin->GND` 的两线模型，内部按 **2kHz** 采样这一脚电平，
并且**只判断高低，不解析占空比**。20kHz 远高于它的采样率，采样点几乎全落在低电平上，
模型就判定"没通电" —— 所以三个工序一律不转。

**改法**：PA7 不再走 TIM3_CH2，改用开关量输出。

| 文件 | 改动 |
|---|---|
| `app/board_port.c` | 删除 `TIM_OC2Init(TIM3,...)` 与 `board_af(GPIOA,7,GPIO_AF_TIM3)`；新增 `pa7_apply(unsigned)`：`motor!=0` 即 `GPIO_SetBits(PA7)`，否则 `GPIO_ResetBits` |
| `app/board_port.h` | 声明 `pa7_apply()` |
| `app/cane_hal.c` | `TIM3->CCR2=...` 改为 `pa7_apply((unsigned)c->motor);`，并补 `#include "board_port.h"` |

**副作用（均为正面）**：

* PA7 不再与 PA6 共用 TIM3 时基，风扇调速那一路彻底独立；
* 电机不再有 PWM 抖动问题，因为根本不产生 PWM；
* `stir` 仍然是 0~100 的百分比，只是现在按"有/无"输出，屏幕和云端上报的数值不变。

**验证**：本机 make exit=0；平台 `build_status=1`，**真错误 0**，text 87524 / bss 22120。

## 2026-10-31（第 7 轮）：DHT11_1 温度报警改成 50℃ 单句播报，去掉“未就绪”播报

### 1. 温度报警线 40℃ → 50℃

| 项 | 改前 | 改后 |
|---|---|---|
| 报警阈值 | 400（40.0℃），写死在 `agri_control.c` | **500（50.0℃）**，宏 `AG_HOT_ALARM` |
| 解除阈值 | 370（37.0℃），写死在 `agri_control.c` | **470（47.0℃）**，宏 `AG_HOT_CLEAR` |

DHT11 量程是 0~50℃，所以 50℃ 就是它读得到的最高一档。顺带把解码上限从
“大于 500 判坏帧”放宽到“大于 550”，`ag_decode_dht()` 与 `ag_accept()` 两处都改了，
否则“刚好 50℃”会卡在边界上，擦边一次就丢一帧。

### 2. 超温话术统一成一句

| 改前 | 改后 |
|---|---|
| 入库工序：“储存仓环境温度过高，请立即采取对应措施” | **“温度过高，请采取相应措施”** |
| 其余工序：“蔗糖厂温度过高，请检查车间通风” | 同上 |

`HOT_ALARM_TEXT` 一条宏管三处：安全页抢页播报、`PAGE_STORE` 整页播报、顶部状态栏
（`cane_gui.c` 显示“温度过高”）。旧的 `STORE_HOT_TEXT` 已删除。报警播报处对这句
仍豁免“安全报警，”前缀，不会念成“安全报警，温度过高…”。

### 3. 拖温度参数时播“温湿度采集未就绪”——已去掉

**根因**：DHT 有效窗只有 5 秒，而且被两处各自判了一次——`board_port.c` 的
`board_millis()-air_at<=5000u`，和 `agri_control.c` 的 `now-air_at_ms>5000u`。
在平台上一拖 DHT11_1 的温度参数，单总线时序被打断，连续几帧解不出来 →
超过 5 秒 → `AG_FAULT_AIR` 置位 → `alarm_reason()` 念“温湿度采集未就绪，请检查环境探头”。
操作员只是在调一个正常值，却听到“传感器没接”。

| 文件 | 改动 |
|---|---|
| `app/board_port.h` | 新增 `AG_DHT_HOLD_MS 20000u`，有效窗 5s → 20s |
| `app/board_port.c` | 有效窗改用 `AG_DHT_HOLD_MS`；读到 0℃/0% 这类量程外帧时丢弃并沿用上一帧（日志 `DHT_RANGE_SKIP`） |
| `app/agri_control.c` | 删掉 `now-c->sample.air_at_ms>5000u` 这条叠加判据，只认 `sample.valid & AG_AIR`，否则会把 20s 窗口又压回 5s |
| `app/cane_runtime.c` | `alarm_reason()` 不再为 `AG_FAULT_AIR` 返回任何话术；`PAGE_STORE` 未就绪时改念“储存仓温度湿度正在采集” |
| `app/cane_gui.c` | 顶部状态栏不再显示“温湿度采集未就绪”（卡片上仍写“未就绪”，需要时看得见） |

`AG_FAULT_AIR` 本来就不在 `CANE_ENV_INTERLOCK` 里，不挡启动、不停产线，所以这几处
只影响“说什么”，不影响“停不停”。串口里的 `DHT_RETRY` / `DHT_FRAME` 日志都保留，
真要排查坏帧，日志照样看得到。
